# AGENTS.md — правила Neironode

## Контекст
- Neironode — сайт небольшой IT-команды, принимающей индивидуальные заказы на разработку и автоматизацию.
- Прочитай `PROJECT.md` для целей и продуктовых решений, `README.md` — для актуального устройства сайта.
- Главная задача сайта: простым языком показать услуги и привести посетителя к личному общению с командой, без лишних форм и конструкторов.

## Разработка
- Первая версия — статический HTML, CSS и JavaScript в `site/`. Не вводи backend, сложные фреймворки и зависимости без потребности.
- Делай адаптивную, доступную и понятную страницу. Стиль — аккуратный минимализм с сильной типографикой, без визуального шума, массы острых прямоугольников и декоративных псевдокнопок.
- Все элементы, выглядящие интерактивными, должны быть действительно интерактивными. JavaScript добавляй ради UX, а не количества кода.
- Не придумывай отзывы, клиентов, сотрудников, гарантии, результаты, цены или контакты. Подтверждённый контакт задаётся через `site/assets/js/config.js`; не используй вымышленные рабочие ссылки.
- Пока сайт разрабатывается и не принимает реальные заказы, GitHub Pages служит удобным публичным предпросмотром, а не заявлением о готовом коммерческом запуске.

## Git — максимально простой процесс
- **Рабочая ветка по умолчанию — `main`.** Для обычных задач изменяй и коммить файлы непосредственно в неё, если среда и разрешения позволяют. Не создавай ветки и Pull Request просто по привычке.
- После каждого успешно проверенного коммита в `main` GitHub Actions публикует каталог `site/` через GitHub Pages. Адрес один: `https://pogroma.github.io/neironode/` (после включения Pages).
- Если Codex Cloud технически требует изолированную ветку, выполни проверки и безопасно перенеси изменения в `main` самостоятельно, если доступно; иначе прямо сообщи, что объединение требуется. Не утверждай, что изменения в `main`, если это не так.
- Перед записью в `main` учитывай её свежую версию: не затирай параллельные изменения, не делай force-push, не объединяй несовместимые изменения вслепую.
- Не публикуй заведомо сломанную сборку. Для рискованных изменений, работы с секретами или после появления реальных клиентов можно использовать отдельные ветки.

## Проверка и документация
- Проверяй доступные тесты, структуру файлов, работу ссылок, мобильный вид и базовые сценарии. Если проверка недоступна, честно укажи это.
- Не добавляй токены, пароли и секреты в репозиторий.
- При существенном изменении проекта обновляй только соответствующие файлы:
  - `PROJECT.md` — концепция, услуги, продуктовые решения и план;
  - `README.md` — структура, запуск, тестирование и деплой;
  - `AGENTS.md` — постоянные правила.
- Не переписывай документацию ради мелких косметических правок.
